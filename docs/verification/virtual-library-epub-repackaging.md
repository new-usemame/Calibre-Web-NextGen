# EPUB packaging identity verification

## Behavior and boundary

The exact-byte edition policy prevented a requested edition from overwriting a different existing book. It also created a duplicate when every EPUB resource was unchanged and only ZIP packaging differed. A native Calibre reproduction imported book 1 again as book 2: the old bookmark remained on book 1, while the new record lacked it.

The fallback now considers only the existing Calibre metadata candidates for the same EPUB format, after preferring any archive whose prepared bytes match exactly. A versioned, framed SHA-256 fingerprint covers every regular resource's exact UTF-8 path, uncompressed length and payload SHA-256 in sorted path order. Empty directory records and ZIP packaging metadata are excluded. This applies the [EPUB 3.3 OCF container boundary](https://www.w3.org/TR/epub-33/#sec-ocf-zip) as a conservative equality rule; it does not establish that arbitrary XML changes are semantically equivalent.

A match retains the existing record and archive without writing its resources or copying reader state. The new source hash remains tied to the owned request; imported SHA-256 describes the original archive actually kept. Policy version 2 is used only for this resource-retained result. Exact-byte retention and new imports retain policy version 1. Both recovery entry points accept proven versions 1, 2 and 3 and recheck the actual contained library file's SHA-256. Older metadata-only retention is reinspected; historical completed receipts remain unchanged. No schema or ownership/grant change is required.

Any changed regular resource, exact path, added/missing file, edition language, font, rights or signature file prevents equality. PDF, KEPUB and other formats retain byte-only matching. Publication XML and text remain byte-exact; path case folding and Unicode normalization are not performed. The narrowly defined locator-only fallback below uses policy version 3.

## Ordinary container locator serialization

A second original legal native Calibre reproduction created a duplicate when only `META-INF/container.xml` used different quotes, spacing, attribute order and namespace prefixes. Publication resources were byte-identical; the old bookmark stayed with the original record.

After raw-byte and exact-resource candidates, policy version 3 can retain an existing EPUB when only the ordinary locator serialization differs. It requires the OCF namespace, `version="1.0"`, exactly one `rootfiles` element containing exactly one empty `rootfile`, only the standard attributes, the same exact package path and `application/oebps-package+xml` media type, and whitespace-only element text. XML comments, namespace prefixes, attribute order, quotes, character references and legal encoding differences may vary. The same validated ZIP pass computes both version 2 and version 3 fingerprints, sharing the existing work and candidate limits.

Unknown attributes/elements or namespaces, `xml:base`, links, multiple rootfiles, changed text, DTD/entities and processing instructions anywhere disable version 3. Packages containing `META-INF/signatures.xml` keep exact-resource matching only. Unsupported locators can still match under the existing exact-byte or exact-resource rule. Every other path and payload—including OPF metadata, language, identifiers, spine, chapter content, fonts, rights and encryption resources—must remain exact. This is a conservative [ordinary OCF locator comparison](https://www.w3.org/TR/epub-33/#sec-container-metainf-container.xml), not general XML canonicalization or a whole-publication conformance check.

The receipt preserves the downloaded-source hash and actual retained-archive hash. Both recovery entry points require current contained stored bytes to match the committed imported hash; accepting version 3 does not bypass that check. Neither archive nor historical application receipt is rewritten. Existing exact-resource fingerprints retain their version 2 framing.

## Conservative package bounds

Identity requires an ordinary contiguous Stored/Deflated EPUB ZIP with the uncompressed `mimetype` resource first and exact, a bounded namespaced `META-INF/container.xml`, and an existing regular package rootfile. It refuses ambiguous names, duplicate/path-prefix aliases, traversal, symlinks/special files, nonempty directory payloads, encryption, unknown extra fields, ZIP64 layouts, hidden/gapped/overlapping local records and inconsistent central/local headers or data descriptors. Unsupported packaging falls back to a separate record; these refusals are not a general EPUB validity verdict. Nothing is extracted or fetched.

Limits are 100 MiB physical package,200 MiB expanded package,50 MiB member,10,000 actual central-directory entries,1,000:1 compression ratio and2 MiB container XML. The additional comparison scans at most 32 deterministic metadata candidates using a shared 200 MiB archive/400 MiB expanded budget, charged for failed scans too. The raw-byte candidate search remains the preceding policy.

The decoder reads the complete Stored/Deflate stream in bounded chunks. It checks actual output length, CRC and end of stream, including forged declared-size tails, reserved blocks, truncation and trailing compressed data. It uses the documented [Python zlib bounded decompression interface](https://docs.python.org/3/library/zlib.html#zlib.Decompress.decompress). Directory/metadata preflight happens before `ZipFile` allocates its entry list. DTD/entity-bearing container XML, including BOMless UTF-16, has no resource identity.
